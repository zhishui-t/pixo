2. **通透技能落地** —— 按用户给定的技法补齐引擎缺的那一环，让"通透"从产品口号变成可执行路径。

## 背景：本轮调研的五条事实

### 事实 1：「通透」是既定产品目标，但从未落地

R22 任务书写明三个产品目标「通透 / 干净 / 风格化」。其中：

- **干净** → 有 CR-06（噪声指标入键宇宙）+ CR-07（亮度降噪）
- **风格化** → 有 CR-09（风格卡 LUT 注入）+ CR-10（场景预设）
- **通透** → **F01~F10 中没有任何对应项**

它只有名字，没有路径。用户本次给的技法说明，正是在补这个空缺。

### 事实 2：现有「通透包」用的指标，不是「去灰」的指标

`configs/rules/tone_clarity_rules.yaml` 4 条规则，触发指标如下：

| 规则 | 触发指标 | 动作 |
|------|---------|------|
| `dehaze_rule_030` | `haze_proxy ≥ 0.22` | `dehaze.strength += 0.06` |
| `clarity_flat_rule_031` | `0.12 ≤ haze_proxy < 0.22` 且 `tonal_range ≤ 0.46` | `clarity.strength += 0.04` |
| `shadow_open_rule_032` | `shadow_clip_ratio ≥ 0.18` | `tone.shadows += 0.05` |
| `highlight_recover_rule_033` | `preview_highlight_clip_estimate ≥ 0.025` | `tone.highlights = -0.08` |

**这些全都不是「黑场在哪」：**

- `compute_proxy_metrics`（`vision/measure.py:118-164`）三个指标全是 p95/p05 的**范围宽度**型
  （`haze_proxy = 1 - tonal_range/p95`）；
- `measure_global`（`vision/measure.py:167-191`）全是**均值 / 裁切率**型；
- **全仓没有任何「黑场端点位置」指标。**

**可推演的误诊链**：一张黑场上浮到 40/255 的发灰照 → p05≈50/255、p95≈200/255 →
`tonal_range≈0.59` → `haze_proxy≈0.24` → **越过 dehaze 门限 0.22，被判为「轻雾」**。

而 dehaze（暗通道先验，`render/core/enhance.py`）**不重定黑场**；`shadow_open_rule_032`
把暗部往上提，**方向与去灰相反、加重发灰**。

知识层自己记过这个坑：`configs/knowledge/photography_post2.json:172` ——
「阴天发灰最容易诱导去雾过量，警惕色偏与晕圈代价」。

### 事实 3：用户给的技法，知识层已写对，但零实现

`configs/knowledge/photography_tone.json`：

- `:22` 「通透公式：黑场扎实+高光透亮+中灰干净=通透；发灰的本质是黑场上浮，先压回黑场再谈色彩。」
- `:36` 「用曲线/色阶把画面最暗的有效像素重定到接近 0 的基准，直方图左端贴边，发灰感随即消失，是去灰第一步。」
- `:116` 「黑场扎实是通透三要素之首，**重定黑场是去发灰的第一动作**。」
- `:124` 「中灰干净对应通透第三要素，中段灰阶拉开后灰蒙感进一步消退。」
- `:90-91` 「夜景发灰(实测教训)」—— 夜景误用中灰锚定会把夜色推向中灰而整体发灰。

**逐条 grep：无任何实现消费这些卡。**

曲线原语（`render/core/curves.py`）齐备（sRGB EOTF / power / filmic / DCP ProfileToneCurve），
但清一色是 **「参数 → LUT」单向**；没有「直方图 → 参数」的反推。

色彩侧（互补色去杂色）**完全空白**：`colorfulness_proxy` 是 std 型「色彩丰富度」，
不是「偏色方向」；没有任何中性像素偏移度量。

## 技法规格（用户 2026-09-14 补充：抖音「通透」操作法的工程转译）

用户原话：

> 「曲线暗部低端拉到最近的直方图点，高光拉到亮部直到图位置，曲线就变成 `_/-`；
> 然后去除杂色，利用互补色原理；再调 RGB 曲线，这样就通透了。」

拆解为 5 步：① 读直方图端点 → ② 拖曲线端点 → ③ 得 `_/-` 形状 → ④ 互补色去杂色 →
⑤ 调 RGB 曲线做冷暖分离。其中 ①②③ 属 F03，④⑤ 属 F04。

**关键判断：这不是新范式。** `render/core/curves.py:150` 的 `curve_inv_y(xs, ys, y)`
已在做「给定输出反求输入」（现用于 `curve_anchor_target` 的曝光锚点）；
`curve_lut_from_points(xs, ys, n)` 已能把任意锚点集变成 LUT。
所以 F03 的缺口**不在「反推」，而在「没人把直方图端点喂给反推」**。

### F03 规格：直方图端点 → 影调曲线锚点

```
measure:
  p_lo = percentile(luma, 0.5)      # 输入黑点；**不得用 min**（护栏 1）
  p_hi = percentile(luma, 99.5)     # 输入白点
  gap  = 直方图空隙度                # 区分「发灰」与「有雾」（护栏 3）
solve:
  xs = [0, p_lo, p_hi, 1]
  ys = [0, 0,    1,    1]           # 即 `_/-` 三段
lut = curve_lut_from_points(xs, ys) # 复用既有原语，无需新算子
guard:
  重定强度按场景亮度分档；夜景不抬/少抬黑场（护栏 2）
```

### F04 规格：中性轴偏移 → 互补色修正

```
measure:                            # 引擎当前完全空白（事实 3）
  S = { 低饱和像素 | sat < τ 且 非高光 }      # 画面内近中性像素集
  (a, b) = median_lab(S) 的中性轴偏移量       # a: 红-绿轴, b: 黄-蓝轴
solve:
  b > 0 (偏黄) → 补蓝   → B 曲线阴影锚点抬起
  b < 0 (偏蓝) → 补黄   → B 曲线阴影锚点压低
  a > 0 (偏红) → 补青   → R 曲线阴影锚点压低
  a < 0 (偏绿) → 补品红 → G 曲线阴影锚点压低
guard:
  肤色蒙版内不施加（防暗肤色被染黄，护栏 4）
```

### 四条护栏（抖音视频未讲、工程上必须处理）

| # | 坑 | 后果 | 对策 |
|---|----|------|------|
| 1 | 用 `min(luma)` 当黑点 | 单个热噪点即锁死黑场，去灰永久失效 | 取 p0.5/p1 分位数 |
| 2 | 夜景一律拉黑场 | 暗部层次被压死（`photography_tone.json:90-91` 已实测） | 按场景亮度分档，夜景不抬黑场 |
| 3 | 把「发灰」当「有雾」 | 触发 dehaze，但 dehaze 不重定黑场 → 白修；`shadow_open_rule_032` 反向加重 | `gap` 空隙度作为 `haze_proxy` 之外的**第二判据** |
| 4 | 互补色修正全局施加 | 暗肤色被染黄 / 青 | 限定阴影锚点 + 肤色蒙版豁免 |

**护栏 3 是 F02 核心验收断言的直接落点**：黑场端点指标必须能区分「发灰」与「有雾」。

**另注（抖音未讲）**：严格按「把端点拖到直方图起点」是**拉伸**（stretch），
保留全部暗部细节；而实战常做**黑场过冲**（黑点设在起点右侧少许），牺牲极暗换扎实黑场。
两者取舍属 F03 的护栏参数，须由 F02 的 `gap`/堆积度指标驱动，不得写死。

### 三条结论

**1. 朝向 bug（既有脚本，已修）** —— 旧 `scripts/ab_vs_camera_thumb.py` 的缩略图旋转做反了
（NEF 内嵌缩略图已是显示态，不能再套 EXIF 表）。竖拍占语料 **48.4%**，
逐像素 ΔE **虚高 2.91x**。正确表在 `scripts/fit_rp_ccm.py:100-106`。

**2. 病灶 = 色度压缩，不是偏色。**
`da ≈ -2.65 - 0.322·a_cam`（R² 0.57）、`db ≈ +1.04 - 0.341·b_cam`（R² 0.87）；
色度保持率 median 0.827，场景越艳错越多（A ↔ 场景色度 r = +0.51）。
**两端都往 0 收** —— "84% 的 da 为负"只是因为多数场景本身偏暖。
影调侧则是**纯固定偏移**（`dL ~ L_cam` 斜率 -0.027、R² 0.013）。

**3. 修 trim 没出路。** 最优单一全局偏移只回收 A **19%**（残留 81%）；
实测 `render_camera_matched`（per-photo 迭代解 EV+WB）只降 A **16%**，
**B/C 反而变差**，仅 52% 照片变好，0711 反而恶化（3.90 → 5.60）。

### F01 尺子（强制口径，已定型）

**A 整图系统色偏 + B 16×16 分块 + C_raw 逐像素**，以 **cc（ECC 相关系数）作对齐门**（cc ≥ 0.85）。
任何「色准改善」结论必须同时给出 A / B / C 三值；**仅 C 降而 A/B 不动 ⇒ 改善的是错位不是颜色**。
